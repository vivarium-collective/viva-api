# Real, actually-dispatched composite documents — pbg-native vs. chain-dispatch

Both files in this directory are **real output**, not hand-written illustrations. Each was
produced by calling the real registered composite-generator function directly with its exact
resolved kwargs (the chain-dispatch example via `process_bigraph.composite_spec`'s own
`to_document()`; the pbg-native example via `build_lineage_ray_batch_document()` — the same builder
`lineage_ray_batch()`'s own body calls internally, confirmed by reading source that the one step
skipped, `prewarm_lineage_pool()`, only sizes a Ray actor pool and never touches the document —
`to_document()` itself hits a real local-only `ray.init()`/working-dir friction that has nothing to
do with the document's content), run locally against a real, complete ParCa cache (commit `4da4e43`,
downloaded verbatim from
`s3://smsvpctest-shared-sharedbucket60d199d6-abfvwv0day91/ray-parca-cache/4da4e43/` — a real cache,
independent of which dispatch's own params get run against it locally).

## Files

- **`pbg-native-lineage-ray-batch-composite.json`** — `v2ecoli.composites.lineage_ray_batch`, built
  with **dispatch `database_id=288`'s own exact, verbatim submitted overrides** (`n_seeds=1,
  n_generations=1, experiment_id="item109-j3-pbgnative-mechanics", injected_processes={swap_processes:
  {"ecoli-metabolism":"ecoli-metabolism-redux"}, exclude_processes:["exchange_data"], ...}` — pulled
  live from `GET /api/v1/simulations/288`, not approximated), merged with `lineage_ray_batch()`'s own
  registered defaults for every field 288 didn't override (`base_seed=0, emitter="both",
  max_duration_per_gen=3600.0, time_step=1.0, media="minimal", variants=None, config_overrides=None,
  emitter_arg=None` — confirmed `emitter_arg=None` produces no key in the document at all, not a null
  one). **This is the exact document dispatch 288 actually sent** — real, on GovCloud infra, tagged to
  Chris and Eran on sms-ecoli#166/#210 as proof the `injected_processes`/`variants`/`emitter_arg`
  exposure fix (v2ecoli PR#663) works end-to-end. Only `cache_dir`/`out_dir` differ from the real
  dispatch (see the caveat below) — `cache_dir` points at this reproduction's own local downloaded
  cache; `out_dir` reflects local resolution (no `PBG_RESULTS_DIR`/`VIVARIUM_WORKBENCH_SWEEP_DIR` set)
  since 288's own request left it unset and the real container's own resolved value isn't independently
  recorded anywhere outside that container. **Corrected 2026-09-04** — an earlier version of this file
  mixed dispatch 282's own params (`n_seeds=2`, a real `out_dir`) with dispatch 288's `injected_processes`
  content, which was never what either dispatch actually sent; `dump_composites.py`'s own hardcoded
  kwargs for this file also didn't match what was checked in, so the file couldn't previously be
  regenerated by running the documented reproduction steps. Both are now consistent — running step 2
  below reproduces this file exactly. See `../docs/design-pbg-native-for-jim.md` §11a for the fuller
  design trace (that section still describes the general capability; this file is the specific,
  byte-exact real artifact).
- **`chain-dispatch-ecoli-baseline-composite.json`** — `v2ecoli.composites.ecoli_baseline`, built

## How to reproduce this yourself

```bash
# 1. A real ParCa cache -- either download a real one (fastest, matches real infra exactly):
aws s3 sync "s3://smsvpctest-shared-sharedbucket60d199d6-abfvwv0day91/ray-parca-cache/<commit>/" \
  /tmp/real-cache/ --profile stanford-sso --region us-gov-west-1
# ...or build one locally: cd v2ecoli && uv run v2ecoli-parca --mode fast --out /tmp/real-cache

# 2. Run the dump script FROM a v2ecoli checkout (it imports v2ecoli, so needs v2ecoli's own
#    venv/environment) -- this script lives in viva-api's own repo, so pass its full path:
cd /path/to/v2ecoli && uv run python /path/to/viva-api/knowledge/composites/dump_composites.py
```

Both documents are exactly what the real registered composite-generator function builds for the
exact params a real dispatch sent — nothing here is illustrative or simplified. The only fields that
differ from an actual GovCloud dispatch are `cache_dir`/`out_dir` (local paths here, resolved by this
reproduction's own environment, vs. real `s3://` URIs inside the actual dispatched container — see
each file's own entry above for exactly which value is a real request field vs. a local-only
resolution).
