# State of the Union — CD2 Dispatch Readiness

*Generated 2026-09-03. Living document — expect this to be updated as priorities shift; check git history for prior versions rather than assuming this snapshot stays current indefinitely.*

## Where we were

The CD2 MVP is defined by four non-negotiable dispatch deliverables (sms-ecoli issue #166, owned by Chris Long): Run 1 (PNNL strain 20_K4), Run 2 (PNNL strain 11_J3), Run 3 (MG1655 antibiotic-cocktail MIC), and Run 4 (violacein). All four need to run fully remotely, on GovCloud, through a dispatch mechanism whose correctness is actually proven — not assumed.

**Chain-dispatch turned out not to be process-bigraph-native, and had a severe latent bug.** Chain-dispatch — the mechanism behind the proven 1000-seed × 10-generation cd1 benchmark — is an external AWS Batch job-dependency orchestrator with no awareness of process-bigraph itself: each generation is a separate container invocation, chained via `dependsOn`. Investigating a throughput discrepancy against the newer pbg-native mechanism (below) surfaced a severe, previously-unknown bug: every chain-dispatch generation since a mid-July composite-id unification silently ran a plain, non-division-gated build for exactly one simulated second, regardless of the requested generation count. Confirmed both from source and empirically — three "generations" of the same real production campaign were byte-for-byte identical files. This called every `cd1_*`/`ptools_*` analysis artifact ever computed from a multi-generation chain-dispatch campaign into question. Fixed (viva-api `v0.9.84`, live) and definitively proven via an MD5 comparison across three genuinely distinct generations.

**A genuinely process-bigraph-native dispatch mechanism was designed, built, and proven at scale.** Rather than continue investing in chain-dispatch's own orchestration, the design shifted to wiring N `LineageProcess` nodes directly into one composite's state tree, each addressed through process-bigraph's real `ray:` protocol — the same mechanism already proven for spatial multi-agent colonies, applied here to independent lineages instead. This is `v2ecoli.composites.lineage_ray_batch`. The central open risk — does real structural cell division survive a `ray:` actor boundary at meaningful scale — is resolved: a real 16-node AWS Batch multi-node-parallel dispatch produced real division on real infrastructure, confirmed from actor-level logs and S3 output, not just a status field.

**Generalized, composite-agnostic dispatch infrastructure was built alongside.** `/compose/v1` gained `document` (raw process-bigraph document submission), `simulator_id` (caller-selectable commit), and `compute_backend` (SLURM/Ray) parameters. A new `atlantis composite run` CLI command fires the identical request a hand-written dispatch script would build, with a raw-JSON escape hatch for anything not yet a named parameter. Both are real, tested, and — for the CLI — CI-green and open for review.

**Two structural gaps in the pbg-native design were investigated, and one turned out much smaller than first thought.** `lineage_ray_batch` initially appeared to lack any way to inject strain-specific processes or run multiple variants — a serious gap, since without it pbg-native could not run any real CD2 config. Triple verification (explicitly demanded before this was accepted as fact) found the underlying capability already existed one layer down, in `LineageProcess` itself; the actual gap was a thin, three-parameter exposure fix in the composite wrapper. Built and proven on real infrastructure: a real chain of dispatches showed `injected_processes` correctly reaching a real `ray:`-addressed actor, with a real strain-specific process swap executing before hitting an unrelated, pre-existing bug in the swapped-in process's own code (not a dispatch defect). The second gap is real and confirmed, not yet closed: the auto-triggered post-completion analysis mechanism does not read the hive-partitioned parquet output pbg-native lineages actually produce, so a pbg-native dispatch currently completes with no retrievable rolled-up analysis, only raw per-lineage output.

**Real infrastructure blockers for CD2 Runs 1 and 2 were found and fixed.** Run 1's own composite was hardcoded out of chain-dispatch's reachable set entirely; fixed via a caller-selectable `composite_id` field. Both runs share a second gap — a strain's real identity depends on a second, local-only script (`build_new_gene_cache.py`) composing an expression level on top of an already-built ParCa cache, with no way to run that step remotely; this is now built, deployed, and live. What remains for both runs is upstream science, not infrastructure: sms-ecoli's own strain-parameterization effort (issue #169) has not yet converged on a validated K4/J3 parameter set. Chris has directly corrected an earlier framing that conflated his *ongoing* parameter optimization with *execution readiness* — he has a candidate strain ready to dispatch today, with the expectation of promoting a better one later as the science matures. The two should not be conflated going forward.

**Reference and dispatch-tooling content was consolidated.** A private, ad hoc collection of backlog notes, design docs, and dispatch scripts — previously scattered across a nested git repo and two fragile worktrees — has been reorganized. Backlog notes remain in their existing private location. A curated set of composite references, dispatch-architecture design docs, and the generic dispatch scripts now live under `viva-api/knowledge/`, tracked normally in this repo, reachable identically whether a session is rooted at the multi-repo workspace parent or inside this repo directly.

## Where we are going

Three priorities, in order, all scoped for now to canonical seed × generation ("s×g") dispatches — spatial multi-agent colony dispatch is important but explicitly not the current focus.

**Priority 1 — prove the pbg-native design is complete, correct, and reproducible for CD2 Runs 1 and 2, via the `atlantis` CLI, against the real composites already in use.**

1. **Merge the two pieces of already-built, already-proven work sitting open.** The injection/variant exposure fix and the `atlantis composite run` CLI are both implemented, tested, and verified against real infrastructure; neither has landed. This is the fastest, lowest-risk step available and unblocks everything after it — there is no new engineering here, only completing review.
2. **Close the analysis-mechanism gap.** A pbg-native dispatch that runs correctly but produces no retrievable analysis is not a usable result for CD2's purposes. This needs the auto-analysis mechanism taught to read the real per-lineage parquet output pbg-native actually writes, plus a related, smaller fix so an analysis job's live status is visible through the same endpoint callers actually poll (rather than only through a separate per-ID lookup). Until this closes, step 3 below cannot produce a complete result, only a partial one.
3. **Fire a real CD2 Run 1 or Run 2 dispatch through the pbg-native path, against a real, ready candidate strain.** Chris has one available now. This is the actual target this priority exists to prove — real composite, real strain-specific configuration, via the `atlantis` CLI, end to end through to a retrievable analysis result. This directly answers the still-open question of whether the dispatch mechanism is ready for his actual candidate today, verified rather than summarized.
4. **Repeat for the other run, and resolve Run 1's own composite question specifically.** Priority 1 names both runs; Run 1's real composite is architecturally distinct from the one the pbg-native wrapper was built and proven around, and whether it slots into the same dispatch shape without further work needs to be confirmed directly, not assumed from Run 2's success.

**Priority 2 — once Priority 1 is solid, prove the same conditions hold through the vivarium-workbench UI**, the preferred mode of interaction for at least one active collaborator. A UI dispatch panel mirroring the CLI's own parameter surface has been built and unit-tested, but has never been exercised through a real, live, visually-confirmed dispatch. This priority is explicitly sequenced after Priority 1 — the underlying mechanism should be proven once, directly, before validating a second surface on top of it.

**Standing, threaded through the above rather than sequenced separately — keep Chris current, with something he can actually run.** As each piece of Priority 1 lands, the right unit to hand him is not a status update but a short, concrete guide tailored to his own real CD2 configurations: the exact command, the exact flags, what to expect back. The goal is for him to be able to run this himself going forward, not to wait on a report each time.

**Explicitly deprioritized, not abandoned.** Colony (spatial multi-agent) dispatch has no UI path today and real remaining design questions of its own — genuinely important, but behind the above.
